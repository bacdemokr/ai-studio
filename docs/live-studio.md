# Live Agent Studio runtime

## Execution path

Stage 3 accepts direct specialist messages and `/plan` requests coordinated by Casey. The fixed event-planning workflow, its preparation jobs, survey endpoints and event-package UI are retired. Old event jobs are excluded from current state and cannot be resumed or retried. Historical files remain on disk.

Mission Control starts empty, then shows the current plan’s actual assignments, contributions and decisions. Results shows files and the response from that plan only. The active team is Casey, Vera, Cody, Ada, Iris and Scout; legacy role indexes remain reserved for saved workspace compatibility.

## Agent collections and ownership


The session cookie authenticates the participant; `X-BaC-Agent` selects one of their agents for each request. The server checks collection ownership for all agent-scoped reads and writes. Selection lives per tab, and stale polls cannot replace the newly selected workspace. No global “current agent” redirects another tab.

The `agents` table maps agent IDs to participants. Migration reuses the original participant ID for their first agent, preserving its native ID, workspace, queued jobs, reset timestamp and phone pairing. Added agents get independent IDs. One attendee may create up to 12 personal agents; the total pending-job budget remains three across that collection. Crew missions retain six preset role slots and reject duplicate or foreign assignments. Pending assignments prevent persona/skill edits until the mission finishes or is cancelled. Reset applies only to the selected agent’s board; other agents keep their tasks.

## What the UI observes

Events are actual app task starts/completions, role handoffs, survey-informed replanning and file writes (older missions can still expose equipment decisions). A character walking to a station is a visualization of a task state. It is not a fine-grained native tool trace, hidden reasoning, or a measured indication that a tool is currently running. Read underlying artifacts to inspect the work. Personal app-builder HTML uses a script-enabled iframe without same-origin permission and with a restrictive no-network CSP. Event webpages use inert, sanitized HTML: scripts and network access are blocked. Downloads also include a restrictive CSP.



Vera's structured question labels populate the app-hosted survey. If the response lacks them, the UI explicitly identifies the built-in English fallback. Public `/survey/<random-token>` pages accept bounded anonymous responses; an anonymous browser ID makes repeated submissions updates rather than extra votes. Aggregate reports and replanning require the owning participant/agent session. No raw browser IDs are exposed. This is a trusted workshop LAN survey, not an identity-verified public voting service. Agent deletion revokes its links and deletes its responses. The app does not publish Google Forms or send promotional mail.

## Optional integrations

### Web search

Website reading and weather work without a search account. Persistent Brave key configuration is disabled; a session-only search-provider setup is not implemented. OpenShell-protected agents use sandboxed curl and curated permissions instead of host-side web tools.

### OpenShell

OpenShell is separate from OpenClaw. Start with an installed, working OpenShell CLI and gateway; the first protected run now automatically prepares the OpenClaw integration (the host CLI `./bac dev openshell enable` remains available). It installs `@openclaw/openshell-sandbox@2026.9.4` if needed, prepares a host-owned deny-by-default policy, and uses **mirror** mode. Outdated integration settings are repaired on the first protected run. Concurrent setup attempts are serialized; setup errors stop the protected request. Setup requests a safe gateway restart to reload plugin registration; it checks readiness before continuing. It preserves the operator's gateway/workspace selection. The default is OpenShell off; only personal agents explicitly selecting protection get `mode=all`, backend `openshell`, **agent scope** and read/write workspace access. Dylan also uses this protected runtime, with `blogs.nvidia.com:443` pre-approved for read-only requests by `/usr/bin/curl`. Other preset roles use `mode=off`. His Python research tool invokes curl inside the sandbox, never a host web tool. Policy activation is checked during preparation and before each direct chat or event turn.

The Hiring and Policies tab save a personal agent's protection choice. The next mission writes its native configuration. A live `agents.list` identity fingerprint must match the new tool/sandbox configuration before sending a model request, including when switching off → on. A missing OpenShell setup fails closed. Mirror mode keeps host uploads and shared briefs available inside the sandbox.

Protected agents have host-side `web_fetch` and `web_search` disabled. Their internet reads use native `exec` with `host=sandbox` and `/usr/bin/curl`; a caller cannot redirect that configured executor to the gateway. Automatic provider attachment is disabled, and new sandboxes start with an empty network allowlist. This limits **tool network access**: shared inference runs on the host and is outside this policy. Browser automation is not enabled.

**Approved websites** lists five curated groups: arXiv, weather/city lookup, Zurich visitor pages, Wikipedia search, and the public GitHub API. The weather group covers api.open-meteo.com, geocoding-api.open-meteo.com and wttr.in. Groups are approval shortcuts: saved approvals and the approved list contain one entry per exact hostname, without overlaps. Each hostname can be revoked independently. Existing group-shaped records are expanded for display while their original native policy is verified; the next explicit policy edit stores the individual grants. Pending requests may also propose an exact validated public hostname. Approval permits only the listed HTTPS destinations and read-only REST access for `/usr/bin/curl`. These demo controls never accept arbitrary YAML, shell commands, providers or credentials. Selecting a skill alone grants no network access. Switching off retains earlier approval choices; re-enabling requires checking the current sandbox policy before a mission. If a sandbox was recreated, reapply saved approvals explicitly.

The API resolves the participant-owned native agent to sandbox names through `openclaw sandbox list --json`; it never guesses or accepts a browser-supplied sandbox name. It updates that sandbox with `openshell policy set --wait`, then verifies the effective policy and its **loaded** revision against the desired permissions. Host/global policy is reported for review and is never overwritten. Pending, failed or mismatched updates remain unconfirmed and block protected missions. Mutations require idle agents, owner/session checks and CSRF. Approval history is stored separately from sanitized OpenShell access logs; no raw logs or credentials reach the browser.

`./bac dev openshell check` reports gateway state and native sandboxes. Configuration alone is not enforcement proof. On the actual Spark, perform this acceptance sequence:

2. Create a personal agent with Weather lookout and Web explorer, with OpenShell on. Ask for Zurich's current weather. Its first task provisions the sandbox; confirm a matching deny log in Policies, not merely a generic fetch failure.
3. Approve **Weather & city lookup**, verify the loaded revision and exact three destinations, then retry and inspect the live result and matching allow log.
4. Request Wikipedia search while it remains unapproved; confirm it is denied. Revoke weather, retry weather, and confirm denial again.
5. Switch this agent off and run its standard weather tool; another protected agent must remain blocked. Reload and check saved choices. Do not change a mode while that agent has pending work.

Local tests use explicit model/policy fixtures for this sequence. Actual sandbox enforcement, endpoint responses, filesystem restrictions and real model behavior still require the Spark checks above.

Without OpenShell, native read/write/edit tools can access user-requested host paths (`tools.fs.workspaceOnly=false`); host OS permissions still apply and workspace remains the default output location. Protected agents use workspace-only native file tools and user uploads. Website approvals change actual OpenShell network rules; they never import host files or write back to host paths. Exec, process, browser, nodes, gateway, cron, messaging and cross-agent session tools are denied; the BaC orchestrator performs controlled handoffs. These app/native tool guards are not an OS isolation boundary. Use this deployment on a trusted workshop network, not as a public adversarial multi-tenant service.

## Storage and deployment

`~/.local/share/bac-demo` (override with `BAC_DATA_DIR`):

- `models/`, `runtime/vllm-env/`: model weights and vLLM installation.
- `openclaw/node/`, `openclaw/package/`: private supported Node and pinned OpenClaw.
- `openclaw/policies/`: host-owned initial and per-agent policy documents, outside editable agent workspaces.
- `openclaw/state/`: native configuration and OpenClaw conversation state.
- `studio/studio.sqlite`: participants, personal agents, queue, handoffs, schedules and pairing state.
- `studio/workspaces/`: persona/skills, uploads, memory and output files.
- `demo/releases/`, `demo/current`, `demo/previous`: immutable application releases.

`./bac dev update` changes only the application release and restarts its service. It preserves the LLM, OpenClaw, agent files and database. Managed updates and rollback refuse pending missions or policy changes; finish or stop them in the app first. An unexpected server interruption still marks running tasks as needing attention. Rollback changes application code, not participant data. The attendee reset archives only the selected agent’s visible board and cancels pending work; it preserves files/memory and refuses to run during active inference. A browser profile isolates participant sessions on non-operator access; localhost is the shared operator collection.

### Local macOS OpenShell host

On Apple Silicon, the official OpenShell installer provides a Homebrew-managed gateway and VM driver. The VM driver must be explicitly selected; it is not auto-detected. This preview host uses OpenShell 0.0.116, `compute_drivers = ["vm"]`, the bundled driver in `/opt/homebrew/opt/openshell/libexec`, and `e2fsprogs` for ext4 guest disks. `bootstrap_image` uses the same OpenClaw image as the plugin (`ghcr.io/nvidia/openshell-community/sandboxes/openclaw:latest`) to avoid the 0.0.116 VM prepared-image path that failed locally with `prepared image disk missing /image-rootfs`. The first sandbox downloads and prepares its images. The app automatically prepares the pinned OpenClaw integration once the host runtime is installed; it never treats a configured plugin as proof that a sandbox has started. OS runtime installation remains a host prerequisite on a new computer.

### Compact demo scope and output-limit recovery

By default, `/plan` targets a small working desktop demo with the minimum necessary specialists. Design specs target 60 lines / 600 words; handoff summaries target 120 words. Explicit requirements take precedence. Forwarded history is capped at 8,000 characters; contribution summaries are bounded and omit tool activity, while saved files remain available for inspection.

An explicit model output-limit error, a tool call truncated at the output limit, or a file-write command returned as plain text allows one fresh-session retry per plan, for either a specialist or a Captain decision, provided at least 30 seconds remain in the existing time budget. The retry inspects saved work and finishes essentials without repeating successful actions. The runtime checks native transcripts for unexecuted text-form write commands even when a later summary claims success. It never executes the printed command itself. Code recovery requests a complete minimal page first (target under 6,000 characters), followed by small native edits. Other errors do not trigger this retry. A second output-limit failure preserves partial work and stops; it is never labelled complete automatically.

Research quality for compact demos: Scout targets two relevant questions, prefers topic-specific source indexes over generic homepages, and aims to stop after one or two useful articles. The prompt budget is at most five fetch attempts including failures, reserving two for a fallback source; this is model guidance, not a tool-enforced quota. Reputable secondary reporting is allowed after publisher failures unless the user requests official-only sources. Explicit policy denials must not be bypassed.
